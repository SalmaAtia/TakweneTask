# DECISIONS.md

This project was built with **Claude Code** over three sessions. I used it as a pair programmer: it wrote most of the code, and I set the architecture, reviewed every change before committing, and pushed back where I disagreed. This file explains which is which, as honestly as I can.

---

## Architecture at a glance

- **Clean Architecture for layering, DDD tactical patterns inside the domain.**
- **Aggregates:** `Track` is the aggregate root and owns its `TrackDistribution`s, because a distribution has no meaning without its track and the status rules span both. `Artist` and `Dsp` are their own aggregates. Aggregates reference each other by ID only.
- **Value objects:** `Isrc`, `Email`, `CountryCode`. They validate on creation, so an invalid ISRC can't exist in the domain.
- **Domain managers** handle rules that need a repository: artist exists, ISRC unique, email unique, DSPs exist. Single-aggregate rules (status transitions, no duplicate DSP per track, "Distributed requires a Live distribution") are methods on `Track`.
- **Dependency direction:**
  - `Domain` holds entities, value objects, repository interfaces, `IUnitOfWork` and managers.
  - `Application` holds app services, DTOs and validators, and references Domain only.
  - `Infrastructure` holds EF Core, repositories and migrations, and also references **Domain only**.
  - `Api` holds controllers, JWT and DI wiring.

  I deliberately kept Infrastructure from referencing Application. It only implements interfaces the domain declares, so it never needs to know about use cases.
- **Shared project** for constants and enums (see below).

## 1. What did AI generate, and what did I write or modify?

### Generated by Claude Code (reviewed by me)
- The solution scaffold, EF Core configurations, migrations and seed data.
- Entities, value objects, managers, repositories, app services, controllers.
- FluentValidation validators and the global exception handler (ProblemDetails).
- JWT setup, login endpoint and Swagger auth.
- The test project: domain unit tests, manager tests with in-memory fake repositories, and API integration tests with Testcontainers.
- The whole Angular app:
  - scaffold, models, services and interceptors
  - track list with a URL-synced status filter and loading, empty and error states
  - track detail with a 404 state and a back link that keeps the filter
  - login, plus the Distribute and Change-status actions
- README content.

### My decisions and changes
- **Switched the architecture to DDD.** Claude Code's first draft was plain Clean Architecture with anemic entities and logic in services. I had it refactored into aggregates, value objects, factory methods with private setters, and domain managers, while keeping the Clean Architecture layering the task requires.
- **Chose where interfaces live.** Repository interfaces and `IUnitOfWork` are in Domain, so Infrastructure depends on Domain only.
- **Chose FluentValidation** for request-shape validation. Business invariants stay in the domain.
- **Unified the data access path in app services** (details in section 3).
- **Added the "mark distribution Live / Rejected" endpoint and UI.** Claude Code pointed out that nothing could make a distribution Live, so the `Distributed` status was unreachable. I decided this endpoint was needed to make the workflow complete.
- **Moved hard-coded values into a Shared project.** Max lengths, validation limits, enum definitions and other magic values now live in one place. Changing a rule (e.g. title max length) changes the EF configuration, the validators and the domain checks together, instead of three copies drifting apart.
- **Chose session storage over local storage** for the token on the frontend (section 2).
- **Chose a single configured demo user** over a users/roles table, since the task only requires JWT protection. In production I'd use ASP.NET Core Identity or an external identity provider (e.g. Entra ID, Auth0) with refresh tokens.
- Reviewed every diff, picked which of Claude's suggestions to adopt, and wrote or approved all commit messages.

## 2. Security issues found (or introduced) and how I handled them

| Issue | Where it came from | How I handled it |
|---|---|---|
| **Database `sa` password in the public example config** | Introduced when pushing to a public repo | Replaced with a placeholder; the real value now comes from user-secrets / environment variables. It was a local Docker dev password only, but it's still in git history, so I rotated it. Lesson: example configs must never contain real values, even "dev only" ones. |
| **JWT signing key in config** | Risk in the default setup | The key lives in user-secrets. `appsettings.json` has placeholders only, and the app fails fast at startup if the key is missing or shorter than 256 bits. |
| **Token storage in `localStorage`** | AI's first frontend version | Moved to in-memory plus `sessionStorage`, so the token doesn't persist after the tab closes. This is still readable by JavaScript if there's an XSS bug. The proper fix is an httpOnly, SameSite cookie, which I left out of scope. |
| **Password handling for the demo user** | — | The password is stored as a hash, never compared as plain text. Login failures return a generic 401 that doesn't reveal whether the username or the password was wrong. |
| **Mass assignment** | Common AI pattern of binding entities directly | The API only accepts request DTOs. A client can't set `Status` on create, because `Track.Create` always starts at `Draft`. |
| **Information leakage in errors** | — | The global exception handler returns ProblemDetails and hides stack traces outside Development. |
| **Race on unique values (ISRC, email)** | AI's first version only checked uniqueness in code | Unique indexes in the database, and a unique-violation `DbUpdateException` maps to 409, so two concurrent requests can't both succeed. |
| **CORS** | — | Restricted to the configured Angular origin, not `AllowAnyOrigin`. |
| **Client trusted for status rules** | — | The "Change status" UI currently offers every status, but the API is the authority. Invalid transitions are rejected by the `Track` aggregate with a 409, whatever the UI sends. |

I also checked whether committing `UserSecretsId` was a problem. It isn't: it's an identifier for the local secrets store, not a secret.

## 3. One thing the AI got wrong that I had to fix

**Split data paths between repositories and managers.**

Claude Code's design had app services **read** aggregates directly from repositories, while all **writes and updates** went through the domain managers. A single app service therefore talked to the same aggregate through two different objects.

**Why it was wrong:**
- **Inconsistent:** there was no single answer to "how does this service get a Track?". It depended on whether the operation was a read or a write.
- **Harder to read:** to follow one use case you had to jump between repository and manager to see which one was really in charge.
- **Risky:** a write path could load the aggregate one way and a read path another, e.g. with or without its distributions or tracking. That makes subtle bugs easy, like updating a Track that was loaded without its distributions.

**What I changed:** each app service uses **one source per aggregate**: either its manager or its repository, never both. Reads moved into the managers too, so the manager is the single entry point for that aggregate. Claude Code updated `CLAUDE.md` with this rule so later sessions followed it.

### Other things tests caught
- **Release dates shown a day early in some time zones.** A date-only value was being handled as a full timestamp and converted to local time. Fixed by treating release dates as date-only end to end.
- A few smaller issues during the frontend work, all fixed before commit.

## Known limitations / what I'd do next

- Store the token in an httpOnly cookie instead of `sessionStorage`.
- Only offer the *valid* next statuses in the Change-status UI. The API already enforces them.
- Use `AsNoTracking` on remaining read paths in the Artist repository.
- Consider moving config key names (`"Jwt"`, `"DefaultConnection"`) into the Shared project too.
- Replace the demo user with ASP.NET Core Identity or an external identity provider, with refresh tokens and role-based permissions.
